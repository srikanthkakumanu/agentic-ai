1. What is Agentic Coding?

Agentic Coding is repository-level software development where Claude Code can reason, inspect files, edit code, run commands, use tools, invoke workflows, delegate to subagents, and iterate until a bounded coding task is complete.

Precise definition: Agentic Coding is not merely asking AI for code snippets. It is giving Claude Code controlled autonomy inside a repository so it can complete implementation, testing, review, and validation tasks under explicit engineering boundaries.

3. The Core Autonomy Boundary

The thin line is not whether Claude edits code. The thin line is which decisions Claude is allowed to make without asking you.

Claude may do

Read source files, implement bounded features, add tests, run local build/test commands, fix failures caused by its changes.

Claude must ask

Add dependencies, change public API contracts, alter business rules, modify deployment manifests, rename modules, delete files.

Claude must never do

Read secrets, use production data, disable tests, log sensitive payment data, run destructive commands, make production calls.

7. Step 1 — Write CLAUDE.md

CLAUDE.md is the always-on project memory. Keep it concise, directional, and stable.

# CLAUDE.md — Payment Authorization Service

## Purpose
This repository contains the Payment Authorization Service for card and wallet transactions.
Claude Code helps implement, test, refactor, and review bounded code changes.

## Primary Stack
- Java 21
- Spring Boot 3.x
- Maven
- PostgreSQL
- Flyway
- Kafka
- Redis
- JUnit 5
- Testcontainers
- OpenAPI

## Architecture Style
Follow layered architecture:
1. API layer: controllers, request/response DTOs
2. Application layer: use cases and orchestration
3. Domain layer: business rules and domain models
4. Infrastructure layer: database, Kafka, Redis, external clients

Do not put business logic in controllers, repositories, Kafka consumers, or mappers.

## Agentic Coding Autonomy
Claude may autonomously:
- Explore the repository
- Read source and test files
- Modify Java, test, OpenAPI, and documentation files
- Add tests
- Run Maven test commands
- Fix compile and test failures caused by its changes

Claude must ask before:
- Adding dependencies
- Changing public API behavior
- Changing payment authorization business rules
- Editing production deployment manifests
- Modifying existing Flyway migrations
- Deleting files

Claude must never:
- Read secrets or credentials
- Disable or delete tests
- Log sensitive payment data
- Use production data
- Make production calls

## Required Workflow
For every non-trivial change:
1. Understand the requirement
2. Inspect relevant files
3. Create a concise implementation plan
4. Implement the smallest safe change
5. Add or update tests
6. Run targeted tests
7. Summarize files changed, behavior changed, and tests run

8. Step 2 — Write Scoped Rules

Rules reduce ambiguity. They should be specific, short, and enforceable.

.claude/rules/java.md

# Java Rules

- Use Java 21.
- Prefer constructor injection.
- Keep business logic in domain/application layers.
- Do not introduce Lombok unless already used.
- Do not represent domain concepts as Map<String,Object>.
- Never log PAN, CVV, tokens, secrets, or full payment payloads.

Expected domain objects:
- PaymentAuthorization
- MerchantAccount
- CardInstrument
- AuthorizationDecision
- IdempotencyKey

.claude/rules/testing.md

# Testing Rules

Use:
- JUnit 5
- AssertJ
- Mockito
- Testcontainers

Every feature change needs tests for:
- Success path
- Validation failure
- Domain failure
- Idempotency behavior where relevant

Claude must not:
- Delete tests
- Weaken assertions
- Mock the class under test
- Replace meaningful assertions with assertNotNull

9. Step 3 — Write Skills for Repeatable Workflows

Skills give Claude a reusable procedure. This is where you intentionally grant feature-level coding autonomy.

# Implement Feature Skill

Use this skill when the user asks Claude to implement a feature.

## Workflow
1. Restate the requirement.
2. Identify impacted areas:
   - API
   - application service
   - domain model
   - repository
   - Kafka/eventing
   - database migration
   - tests
   - documentation
3. Read relevant files.
4. Produce a short implementation plan.
5. Implement the smallest complete change.
6. Add or update tests.
7. Run targeted tests.
8. Run broader validation if needed.

## Constraints

- Add dependencies without approval.
- Modify existing Flyway migrations.
- Delete tests.
- Touch secrets or production configs.

11. Step 5 — Configure Permissions

settings.json is where autonomy becomes operational. It decides what Claude can do, what requires approval, and what is blocked.

{
  "permissions": {
    "allow": [
      "Read(src/**)",
      "Read(docs/**)",
      "Read(pom.xml)",
      "Edit(src/**)",
      "Edit(docs/**)",
      "Edit(openapi/**)",
      "Bash(mvn test)",
      "Bash(mvn -q test)",
      "Bash(mvn -q verify)",
      "Bash(git diff *)",
      "Bash(git status *)"
    ],
    "ask": [
      "Edit(pom.xml)",
      "Edit(k8s/**)",
      "Edit(helm/**)",
      "Edit(.github/**)",
      "Bash(docker *)",
      "Bash(kubectl *)",
      "Bash(git commit *)",
      "Bash(git push *)"
    ],
    "deny": [
      "Read(.env)",
      "Read(.env.*)",
      "Read(secrets/**)",
      "Read(**/*.pem)",
      "Read(**/*.key)",
      "Bash(rm -rf *)",
      "Bash(kubectl delete *)",
      "Bash(curl *production*)"
    ]
  }
}
Rule: Put real boundaries in settings, not only in prose. Prose guides Claude; settings constrain Claude.

12. Step 6 — Add Hooks for Deterministic Enforcement

Hooks are best for actions that must always happen or must always be blocked.

#!/usr/bin/env bash
set -euo pipefail

COMMAND="${1:-}"

blocked_patterns=(
  "rm -rf"
  "kubectl delete"
  "curl .*production"
  "cat .env"
  "cat .*pem"
  "cat .*key"
)

for pattern in "${blocked_patterns[@]}"; do
  if [[ "$COMMAND" =~ $pattern ]]; then
    echo "Blocked unsafe command: $COMMAND"
    exit 1
  fi
done

exit 0
Do not use hooks for subjective reasoning. Use hooks for deterministic checks. Use subagents for review judgment.

13. Step 7 — Add MCP Only When External Context Is Needed

MCP expands Claude’s action space, so it must be introduced carefully.

MCP use caseAllowed autonomyRisk
GitHub issue/PR readingRead-only firstAccidental PR comments or branch changes
Jira ticket lookupRead requirements onlyUsing stale or vague ticket info
Database schema inspectionRead-only schemaData exposure or destructive queries
ObservabilityRead metrics/logs with maskingSensitive production information
Default principle: local repository knowledge first, MCP only when live external state is required.

16. Autonomy Overlap Anti-patterns

Bad: Workflow in every file

Putting implementation procedures in CLAUDE.md, skills, agents, and hooks creates conflicting autonomy.

Fix: global policy in CLAUDE.md, workflow in skills.

Bad: Hooks as reviewers

Hooks should not decide whether architecture is elegant or business logic is correct.

Fix: hooks enforce deterministic checks; subagents review.

Bad: MCP everywhere

Connecting every external tool increases risk, cost, and context noise.

Fix: local docs first; MCP only for live external state.

Bad: Giant CLAUDE.md

A huge memory file makes Claude slower and less precise.

Fix: keep CLAUDE.md lean; route details through rules, skills, and docs.

17. Implementation Checklist

Build the setup

  • Create concise CLAUDE.md.
  • Add scoped rules for Java, Spring, testing, security, database, and API contracts.
  • Create skills for implement-feature, fix-bug, add-tests, and review-change.
  • Create subagents for code review, security review, testing, and DB migration review.
  • Add permission boundaries in .claude/settings.json.
  • Add hooks for unsafe commands and mandatory validation.
  • Add docs/rag/RAG.md for knowledge routing.

Validate the setup

  • Ask Claude to explain the autonomy boundaries.
  • Ask Claude to implement a small feature.
  • Check whether it asks before dependency/API changes.
  • Check whether it refuses secrets/destructive commands.
  • Check whether tests are added and actually run.
  • Check whether the final summary is evidence-based.
Final mental model: CLAUDE.md defines identity and policy; rules define standards; skills define workflows; subagents define specialist delegation; settings define permissions; hooks enforce deterministic checks; MCP expands external capability; RAG routes knowledge.
