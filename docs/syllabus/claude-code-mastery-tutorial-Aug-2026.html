welcome

Claude Code, by workflow type.

Everything in this guide — every markdown file, every JSON config, every prompt, every case study — is organized around one question: which of the three 2026 workflow types are you doing right now? Agentic Coding, Agentic Engineering, or Harness Engineering. Same underlying files you'd learn either way; very different golden templates and prompts once you know which one you're in.

What & Why · The comparison

Agentic Coding vs. Agentic Engineering vs. Harness Engineering

These three terms are real, current 2026 industry vocabulary, not house terms invented for this guide. "AI autonomy is increasing" gets said a lot; these three answer the more useful question — autonomy of what, exactly?

Agentic Coding

Anthropic's own term for what Claude Code fundamentally is: "an agentic coding tool that reads your codebase, edits files, runs commands, and integrates with your development tools." One agent, one task, one session. You describe what you want; the agent plans, writes, runs, and iterates inside that task; you review the diff before it lands. Per Anthropic's 2026 Agentic Coding Trends Report, this is already the dominant pattern — developers use AI this way in roughly 60% of their work.

Agentic Engineering

Andrej Karpathy's early-2026 term for what comes after "vibe coding" stops being fun and starts being production risk: a disciplined Plan → Execute → Verify loop run across a small team of specialized agents — an author, a tester, a reviewer, a security scanner — instead of one agent doing everything. You act as architect and orchestrator, not typist. Anthropic's same 2026 report found developers can fully delegate only 0–20% of tasks even though AI touches 60% of their work; agentic engineering is the attempt to close that gap safely by structuring the workflow, not by trusting the model more.

Harness Engineering

A term that entered mainstream use in early 2026 (Martin Fowler, OpenAI's Codex team, and Anthropic's own engineering blog all wrote about it within months of each other): the discipline of designing the environment an agent operates inside — its tools, its guardrails, its feedback loops, its observability — so that autonomy is actually safe to grant. Not a workflow you run; the substrate every workflow above runs on top of. LangChain proved the point concretely: they moved a coding agent from 52.8% to 66.5% on a benchmark by changing only the harness, without touching the model at all.

None of these replace the other two. In a mature setup you're always doing all three at once: coding a task, inside a multi-agent workflow, inside a harness someone — quite possibly you — engineered. What changes is which layer you're deliberately designing versus just using unconsciously. Files 1–3 below each give that layer a full treatment: what it is, every file it needs with a golden template and a filled example, its prompts, and its case study.

One agent, one task, one session

This is what "using Claude Code" means on a normal Tuesday. You have a scoped task, you describe it, the agent works within a session, and you review the diff. No subagents, no hooks, no MCP — adding those here is premature scaffolding for a workflow that doesn't need it yet.

# CLAUDE.md — Payments Ledger Service

## Architecture
Java 21 / Spring Boot 3 microservice. Exposes REST + gRPC. Postgres (ledger DB),
Kafka topic `ledger.events.v1` for downstream settlement. Deployed on EKS.
Redis for idempotency-key storage (24h TTL).

## Conventions
- All monetary values: `long` cents, never `double`/`float`.
- Every write endpoint requires an `Idempotency-Key` header — see `IdempotencyFilter`.
- Tests: JUnit5 + Testcontainers. Run with `./gradlew test`. No mocking the DB layer.
- Commits: Conventional Commits. PR must reference a Jira ticket (LEDGER-XXXX).
- Log decisions to `NOTES.md` as you go — don't rely on chat history surviving compaction.

## Do not
- Do not modify `schema.sql` directly — use Flyway migrations in `db/migration/`.
- Do not call external payment providers directly from this service; use `payment-gateway-client`.
- Do not add a new runbook without also updating `tools/rag-mcp-server`.

## Tooling
- Team's Claude Code setup ships as one plugin: `/plugin install payments-ledger-toolkit@payments-platform-marketplace`.

1 · Agentic Coding 5 / 5 · Case study

Add a /health endpoint

Deliberately small. This is the whole point of Agentic Coding as a workflow type — it doesn't need more than this to be done well.

  1. CLAUDE.md and CLAUDE.local.md already exist (files 2–3, above).
  2. You type the one prompt from the Prompts file.
  3. Claude Code plans (reads the controller package, the test conventions), writes the endpoint and test, runs ./gradlew test itself.
  4. You review one diff — a controller method and a test file — and merge.

Total new files: zero. Total new primitives: zero. That's correct — a task this size doesn't earn a subagent, a hook, or an MCP server. Reaching for those here would be over-engineering the harness for the task at hand.

2 · Agentic Engineering 1 / 7 · What & why

The Plan → Execute → Verify loop, with an agent team

Once a task needs an author, a tester, and a reviewer with genuinely different concerns, running them all as one undifferentiated Claude Code session stops working — context gets muddled and nothing is isolated. Agentic engineering is Karpathy's name for the fix: define roles, run a Plan → Execute → Verify loop, and let the roles run mostly unattended between the two human checkpoints.

The agent-team model

Industry practice (per Karpathy's framing and how teams like Stripe and TELUS report using it) assigns each concern its own agent rather than one agent doing everything:

RoleResponsibilityMaps to, in this guide
Feature AuthorWrites the implementationThe main Claude Code session, or a dedicated author subagent
Test GeneratorWrites and runs testsA read-write subagent scoped to src/test/
Code / Security ReviewerChecks style, patterns, security — never editsA read-only subagent

Filled examples

.claude/rules/api-rules.md 
---
paths:
  - "src/main/java/**/controller/**"
  - "src/main/java/**/api/**"
---

# API layer rules

- Every write endpoint (POST/PUT/PATCH) must accept and validate an `Idempotency-Key` header.
- Money fields are always `long` cents in request/response DTOs. Never `double`, `float`, or `BigDecimal` on the wire.
- Every new endpoint needs an OpenAPI `@Operation` annotation and an entry in `docs/api-reference.md`.
- Do not return raw JPA entities from controllers — always map to a response DTO.
.claude/rules/testing-rules.md 
---
paths:
  - "src/test/**"
---

# Testing rules

- Integration tests use Testcontainers for Postgres and Kafka — never mock the DB layer or an embedded broker.
- Every new write endpoint needs a duplicate-request test asserting a 409 on a replayed Idempotency-Key.
- Run `./gradlew test` before proposing any diff as done; paste the summary line, not the full log.
- Flaky test allowance: zero. Fix or quarantine in the same PR — do not silently retry.

---
name: kafka-capacity-check
description: Use when asked to size Kafka partitions/brokers for a target throughput, or to review an existing topic's capacity assumptions.
---

# Kafka Capacity Sizing Playbook

Given a target events/sec and average message size, run `scripts/kafka_sizing.py`
rather than estimating the arithmetic by hand:

    python3 scripts/kafka_sizing.py --events-per-sec 650000 --avg-msg-bytes 512 --critical

1. Use `--critical` for any topic touching money movement (forces replication factor 3).
2. Flag if consumer group lag would exceed 2x partition count (rebalancing risk).
3. Always show the script's output, not just the final number.

See `reference/broker-sizing-table.md` for AWS MSK instance-type throughput numbers.
.claude/skills/kafka-capacity-check/scripts/kafka_sizing.py 
#!/usr/bin/env python3
"""Computes recommended partition count and replication factor for a target
Kafka throughput. Referenced by SKILL.md so Claude executes it directly
instead of estimating the arithmetic itself."""
import argparse
import math

PARTITION_THROUGHPUT_MB_S = 10  # see reference/broker-sizing-table.md

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--events-per-sec", type=float, required=True)
    parser.add_argument("--avg-msg-bytes", type=float, required=True)
    parser.add_argument("--critical", action="store_true",
                         help="Set for money-movement topics (forces replication factor 3)")
    args = parser.parse_args()

    throughput_mb_s = (args.events_per_sec * args.avg_msg_bytes) / (1024 * 1024)
    partitions = math.ceil(throughput_mb_s / PARTITION_THROUGHPUT_MB_S)
    replication_factor = 3 if args.critical else 2

    print(f"Target throughput:      {throughput_mb_s:.2f} MB/s")
    print(f"Recommended partitions: {partitions}")
    print(f"Replication factor:     {replication_factor}")

if __name__ == "__main__":
    main()

2 · Agentic Engineering 7 / 7 · Case study

Shipping idempotency enforcement as a 3-agent pipeline

One feature, three roles, two human checkpoints. This is the smallest example that's still genuinely Agentic Engineering rather than Agentic Coding with extra steps.

  1. Plan: you write the objective, constraint, and agent-role assignment into NOTES.md (prompt 6, above).
  2. Execute — author: the main session (or a dedicated author subagent) writes IdempotencyFilter.java.
  3. Execute — tester: idempotency-test-writer adds the duplicate-request test and runs it.
  4. Execute — reviewer: payments-security-reviewer checks both, read-only, reports findings.
  5. Verify: you read the reviewer's report and the test result, then write the Verify section and merge.
src/main/java/com/deriv/ledger/filter/IdempotencyFilter.java 
package com.deriv.ledger.filter;

import jakarta.servlet.*;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;

import java.io.IOException;
import java.time.Duration;

@Component
public class IdempotencyFilter implements Filter {

    private static final Duration TTL = Duration.ofHours(24);
    private final StringRedisTemplate redis;

    public IdempotencyFilter(StringRedisTemplate redis) {
        this.redis = redis;
    }

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest httpReq = (HttpServletRequest) req;
        HttpServletResponse httpRes = (HttpServletResponse) res;

        boolean isWrite = "POST".equals(httpReq.getMethod()) || "PUT".equals(httpReq.getMethod());
        if (!isWrite) { chain.doFilter(req, res); return; }

        String key = httpReq.getHeader("Idempotency-Key");
        if (key == null || key.isBlank()) {
            httpRes.sendError(HttpServletResponse.SC_BAD_REQUEST, "Missing Idempotency-Key header");
            return;
        }

        Boolean firstSeen = redis.opsForValue().setIfAbsent("idempotency:" + key, "1", TTL);
        if (Boolean.FALSE.equals(firstSeen)) {
            httpRes.setStatus(HttpServletResponse.SC_CONFLICT);
            httpRes.getWriter().write("Duplicate request for Idempotency-Key: " + key);
            return;
        }
        chain.doFilter(req, res);
    }
}

To verify it end to end: docker run -d --name ledger-redis -p 6379:6379 redis:7, then ./gradlew bootRun, then send the same POST /payments twice with the same Idempotency-Key via curl — the second call should return 409, exactly as NOTES.md's Plan specified.

3 · Harness Engineering 1 / 6 · What & why

Engineering the environment the agents run inside

Neither of the previous two workflows is safe by accident. A subagent only stays in its lane because a tools list constrains it; a session only avoids leaking a secret because something is watching for that pattern. Harness engineering is the deliberate design of that watching, constraining, and tool-granting layer — the environment, not a task inside it.

Required files

FileRequired?Purpose
.claude/settings.jsonYesDeterministic guardrails (hooks) and permission tiers that don't depend on the model remembering anything
.mcp.jsonYes, once agents need tools beyond the filesystemExplicit, auditable tool orchestration
.claude-plugin/plugin.json + marketplace.jsonRecommended at team scalePackages the whole harness so it's reproducible for every teammate and every new project

Harness engineering doesn't ship a feature, so it doesn't have a feature-shaped case study. Its test is: does a brand-new teammate get a working, safe environment in under five minutes? File 6 of this group is built around exactly that test.

#!/usr/bin/env node
// Keyword/TF-IDF search over local runbooks — no embedding API key required.
import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { CallToolRequestSchema, ListToolsRequestSchema } from "@modelcontextprotocol/sdk/types.js";
import fs from "node:fs";
import path from "node:path";

const RUNBOOK_DIR = process.env.RUNBOOK_DIR || path.join(process.cwd(), "runbooks");

function tokenize(text) { return text.toLowerCase().match(/[a-z0-9]+/g) || []; }

function loadCorpus() {
  const files = fs.readdirSync(RUNBOOK_DIR).filter((f) => f.endsWith(".md"));
  return files.map((file) => {
    const raw = fs.readFileSync(path.join(RUNBOOK_DIR, file), "utf8");
    return { file, raw, tokens: tokenize(raw) };
  });
}

function scoreDoc(queryTokens, doc) {
  const freq = {};
  for (const t of doc.tokens) freq[t] = (freq[t] || 0) + 1;
  let score = 0;
  for (const q of queryTokens) score += freq[q] || 0;
  return score / Math.sqrt(doc.tokens.length || 1);
}

function ragSearch(query, topK = 3) {
  const corpus = loadCorpus();
  const qTokens = tokenize(query);
  return corpus
    .map((doc) => ({ file: doc.file, score: scoreDoc(qTokens, doc), snippet: doc.raw.slice(0, 400) }))
    .sort((a, b) => b.score - a.score).slice(0, topK).filter((r) => r.score > 0);
}

const server = new Server({ name: "ledger-rag", version: "1.0.0" }, { capabilities: { tools: {} } });

server.setRequestHandler(ListToolsRequestSchema, async () => ({
  tools: [
    { name: "rag_query", description: "Answers a question using the ledger service's runbooks.",
      inputSchema: { type: "object", properties: { question: { type: "string" } }, required: ["question"] } },
    { name: "get_stats", description: "Returns how many runbook documents are indexed.",
      inputSchema: { type: "object", properties: {} } },
  ],
}));

server.setRequestHandler(CallToolRequestSchema, async (request) => {
  const { name, arguments: args } = request.params;
  if (name === "rag_query") {
    const results = ragSearch(args.question, 3);
    if (results.length === 0) return { content: [{ type: "text", text: `No runbook matched "${args.question}".` }] };
    const text = results.map((r) => `### ${r.file}\n${r.snippet}...`).join("\n\n");
    return { content: [{ type: "text", text }] };
  }
  if (name === "get_stats") {
    return { content: [{ type: "text", text: `${loadCorpus().length} runbook document(s) indexed.` }] };
  }
  throw new Error(`Unknown tool: ${name}`);
});

await server.connect(new StdioServerTransport());

3 · Harness Engineering 6 / 6 · Case study

Proving a new teammate gets a safe environment in under 5 minutes

Harness engineering's acceptance test isn't a feature demo — it's this sequence, run from a clean checkout.

  1. npm install in tools/rag-mcp-server, then smoke-test it alone: npx @modelcontextprotocol/inspector node index.js — call rag_query and confirm it returns a real passage from runbooks/reconciliation.md, before Claude Code is even involved.
  2. chmod +x .claude/scripts/block-env-file-writes.sh, then test it in isolation: echo '{"tool_input":{"file_path":".env"}}' | .claude/scripts/block-env-file-writes.sh; echo $? → should print 2.

The layered context system

Claude Code isn't "a chatbot with file access." It's an agentic loop — read → plan → act → check — wrapped around a layered context system. Each layer loads at a different time, for a different reason. Core Reference 2 / 9 · Project memory

CLAUDE.md

What it is: a markdown file at your project root. Claude Code walks up the directory tree from your working directory to the repo root, reading every CLAUDE.md it finds along the way, and concatenates them — additive, not overriding.

Where

  • ./CLAUDE.md — project root, checked into git, shared with the team
  • ./CLAUDE.local.md — same directory, gitignored, personal
  • ~/.claude/CLAUDE.md — your global preferences across all projects
  • Nested CLAUDE.md in subdirectories — applies when work touches that subtree (monorepos)

Generate a starting point: run /init inside Claude Code — it scans the repo and drafts one you then edit.

What to put in it

  • Architecture in 3–5 lines ("API Gateway → 6 microservices via gRPC, Postgres per service, Kafka for events")
  • Tech stack and why ("Spring Boot 3, not Micronaut — team expertise")
  • Commands Claude should use (make test, not npm test if that's wrong)
  • Hard rules ("never touch /infra/terraform without asking")
  • Review checklist expectations (idempotency keys, structured logging fields)

What NOT to put in it: full API docs (link instead), one-off task instructions, anything you wouldn't repeat to a new hire twice.

CLAUDE.md 
# CLAUDE.md — Payments Ledger Service

## Architecture
Java 21 / Spring Boot 3 microservice. Exposes REST + gRPC. Postgres (ledger DB),
Kafka topic `ledger.events.v1` for downstream settlement. Deployed on EKS.

## Conventions
- All monetary values: `long` cents, never `double`/`float`.
- Every write endpoint requires an `Idempotency-Key` header — see `IdempotencyFilter`.
- Tests: JUnit5 + Testcontainers. Run with `./gradlew test`. No mocking the DB layer.
- Commits: Conventional Commits. PR must reference a Jira ticket (LEDGER-XXXX).

## Do not
- Do not modify `schema.sql` directly — use Flyway migrations in `db/migration/`.
- Do not call external payment providers directly from this service; use `payment-gateway-client`.

This is the compact version — see Agentic Coding file 2 for the fuller one with a Tooling section pointing at the plugin bundle.

Core Reference 3 / 9 · Delegation

.claude/agents/*.md — Subagents

A subagent is a markdown file with YAML frontmatter, run in its own context window, with its own system prompt, restricted toolset, and independent permissions. This is how you stop one giant session from doing exploration, coding, and review all in one polluted context.

Where: .claude/agents/ (project, shared via git) or ~/.claude/agents/ (personal). Create interactively with /agents.

Built-in, for free: Explore (read-only, fast, runs on Haiku), Plan (gathers context before proposing a strategy), general-purpose (explore + modify). Claude routes to these automatically.

Frontmatter that matters: name, description (write it behaviorally — add "use proactively" to trigger it automatically), tools (narrow allow-list), disallowedTools, model, permissionMode, maxTurns.

.claude/agents/payments-security-reviewer.md 
---
name: payments-security-reviewer
description: Use proactively after any change to files under src/payments/. Reviews for PCI-relevant issues, idempotency gaps, and missing audit logging. Read-only — never edit.
tools:
  - Read
  - Grep
  - Glob
model: sonnet
---

You are a security-focused reviewer for a payments microservice.
For every change, check specifically for:
1. Missing idempotency keys on state-changing endpoints
2. Card/account data logged in plaintext
3. Missing audit trail entries for balance-changing operations
Report findings as a short bullet list with file:line references. Do not fix — only report.

A read-only reviewer like this cannot accidentally edit what it's reviewing — that's the point of the narrow tools list, not an accident. See Agentic Engineering file 3 for a second, read-write example (the test-writer) and how the two work together in a pipeline.

Core Reference 4 / 9 · Just-in-time expertise

.claude/skills/*/SKILL.md

Skills are the newest, most important primitive. A Skill is a folder with a SKILL.md (frontmatter + instructions) plus optional scripts, templates, or reference files. Claude scans the name + description of every skill every session (cheap), but only pulls the full body into context when the task actually matches — progressive disclosure. A project can have 50 skills without bloating every session; a 5,000-line CLAUDE.md would.

Where: .claude/skills/<name>/SKILL.md (project) or ~/.claude/skills/ (personal). Invoke with /skill-name or let Claude auto-trigger it.

Skills follow an open standard (Agent Skills spec) — the same SKILL.md works in Claude.ai, the API, and other adopting tools.

.claude/skills/kafka-capacity-check/SKILL.md 
---
name: kafka-capacity-check
description: Use when asked to size Kafka partitions/brokers for a target throughput, or to review an existing topic's capacity assumptions.
---

# Kafka Capacity Sizing Playbook

Given a target events/sec and average message size:
1. Compute required partition count: throughput ÷ per-partition-throughput-budget (~10MB/s/partition unless told otherwise).
2. Recommend replication factor 3 for anything touching money movement; RF 2 for pure telemetry.
3. Flag if consumer group lag would exceed 2x partition count (rebalancing risk).
4. Always show the formula, not just the number.

See `reference/broker-sizing-table.md` for AWS MSK instance-type throughput numbers.

Core Reference 5 / 9 · Deterministic control

Hooks — not a markdown file

Hooks are shell commands (or HTTP calls) that fire at fixed lifecycle events, configured as JSON in .claude/settings.json. They exist because you can't rely on a model to remember to run a formatter or block a dangerous command every single time — a hook guarantees it.

Common events: SessionStart, PreToolUse (before any tool runs — can block/rewrite), PostToolUse (after completion — auto-format, log, feedback), UserPromptSubmit, Stop, SubagentStop.

.claude/settings.json 
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "scripts/block-env-file-writes.sh" }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          { "type": "command", "command": "npx prettier --write \"$CLAUDE_TOOL_INPUT_FILE_PATH\"" }
        ]
      }
    ]
  }
}

Exit code 2 from a PreToolUse hook blocks the tool call and feeds the reason back to Claude. This is the layer you'd point to if an interviewer asks "how would you stop Claude Code from ever committing a .env file" — the answer is a hook, not a prompt instruction.

Core Reference 6 / 9 · The outside world

.mcp.json — MCP & your RAG answer

MCP (Model Context Protocol) is the open protocol that lets Claude Code call tools outside its built-in set — a database, an issue tracker, a browser, or your own RAG pipeline. Servers are configured in .mcp.json at the project root (commit it) or added via claude mcp add.

.mcp.json 
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}" }
    },
    "ledger-rag": {
      "command": "node",
      "args": ["./tools/rag-mcp-server/dist/index.js"]
    }
  }
}

Which RAG pattern to reach for

  • Lightweight / static corpus → a Skill with reference files Claude greps on demand. No vector DB needed.
  • Real RAG / large, changing corpus → a small MCP server wrapping your embedding + vector store, exposing tools like rag_query, rag_search, index_document.

The tool description field in a custom MCP server is the only signal the model uses to pick the right tool — write it precisely. For a standalone agent/RAG service outside the CLI: that's the Claude Agent SDK — same primitives, embedded programmatically in your own service.

There's no Anthropic-mandated journal.md. ## Decisions

Everything above is just files in your project folder. They work identically no matter which surface you use — none of it changes by workflow type, either. What changes is only how you invoke Claude Code and review its work.

Two ways Claude Code shows up in VS Code

  1. The official Claude Code extension — Ctrl+Shift+X / Cmd+Shift+X → search "Claude Code" → the one published by Anthropic. Bundles its own CLI, gives inline diffs, plan review, @-mentions with line ranges, conversation history. Anthropic's recommended surface.
  2. The standalone CLI — npm install -g @anthropic-ai/claude-code, run claude in VS Code's integrated terminal. Same engine; needed if an environment expects the raw command or scriptable/headless behavior.

Install both before the assessment. Set ANTHROPIC_API_KEY as a shell env var in advance — either surface accepts it, and launching VS Code with code . from that terminal inherits it automatically.

Where the conventions live in the panel

  • Press / for the slash-command surface: /memory, /agents, /mcp, /hooks, /plugin.
  • Or just create CLAUDE.md, .claude/agents/reviewer.md, .mcp.json directly in the file explorer — often faster once you know the shape.
  • The Spark icon (✦) — editor toolbar, Activity Bar, or status bar — opens the panel.

One deliberate choice for a recording: leave approval-gated permission mode on (claudeCode.initialPermissionMode) and narrate your review of each diff before accepting. Auto-accept removes the exact moment you get to demonstrate judgment.

The assessment-day playbook

A recorded, think-aloud assessment isn't testing whether you can write a for-loop. It's testing whether you can direct an AI tool the way you'd direct a senior engineer, and narrate architectural reasoning in real time.

Before you join

  1. Install Claude Code and confirm it runs — don't debug installation on camera.
  2. Set ANTHROPIC_API_KEY as a shell env var in advance; confirm subscription login is active if you use that instead.
  3. Keep a minimal CLAUDE.md template ready to fill in fast.
  4. Do one full test round-trip beforehand — scaffold something, edit a file.
  5. Have a scratch repo with git init already done; commit as you go.
  6. Decide your narration rhythm: state intent before every prompt, state what you're verifying after.

During the assessment

  1. Restate the requirement, sketch the architecture before touching Claude Code.
  2. Write the CLAUDE.md first, narrating why — the single highest-leverage first five minutes.
  3. Use Plan mode and say why you want to see the approach before it touches files.
  4. Delegate isolation/repetition to a subagent, and say so — tie tool choice to a security/process rationale.
  5. Verify, don't just accept — run tests, read diffs, push back out loud when warranted.
  6. Narrate production considerations unprompted — observability, idempotency, rollback, DORA metrics.
  7. Keep a running NOTES.md of decisions and open questions as you go.

An assessment requiring "your API key ready" very likely includes a task where you write or wire up something live. Given how small most live tasks are, you'll most likely be operating in Agentic Coding or a light Agentic Engineering pass (files 1–2) rather than building a whole harness live — but naming which one you're in, out loud, is itself a strong signal of maturity, and it's exactly the vocabulary this guide gives you.
