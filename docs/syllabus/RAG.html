1. What RAG Is

RAG stands for retrieval-augmented generation. Before a language model answers, your program looks up relevant text and puts it in the prompt. The model then answers from that text instead of from memory alone.

An LLM (large language model) is the kind of model behind Claude, GPT, and Gemini. The prompt is the text you send it.

1.1 The Problem RAG Solves

An LLM knows only what was in its training data. It has never seen your company handbook, last week's price list, or a customer's contract.

Ask it about those and one of two things happens. It says it does not know, or it produces a confident answer that is wrong. The second case is often called a hallucination.

You could paste every document into every prompt, but that is slow, costs money, and stops working once you have more text than the model can read at once. RAG sends only the few passages that matter for this question.

Back to top

1.2 The Two Phases: Indexing and Querying

Every RAG system has two parts that run at different times.

Indexing happens ahead of time. You cut your documents into small pieces, turn each piece into numbers, and save them in a database built for searching by those numbers.

Querying happens for each question. You turn the question into numbers the same way, find the saved pieces closest to it, put them in the prompt, and let the model answer.

The name describes the query phase: retrieve the pieces, augment the prompt with them, generate the answer.

Back to top

1.3 The Building Blocks

Six parts appear in almost every RAG system. The rest of the lesson uses these words.

PartWhat it does
LoaderReads a source (file, web page, database row) into plain text.
ChunkerCuts long text into small pieces called chunks, often a few hundred characters each.
Embedding modelTurns a piece of text into a list of numbers called an embedding or vector. Texts with similar meaning get similar numbers.
Vector storeA database that saves chunks with their vectors and can quickly find the vectors closest to a given one. Also called a vector database.
RetrieverThe code that takes a question and returns the best chunks. In Basic RAG it is one vector search. In later types it does more.
LLMReads the question and the chunks and writes the answer.

The number of chunks the retriever returns is called top-K. "Top-4" means the four closest chunks.

1.4 How RAG Has Grown

RAG has evolved far beyond the original "embed, retrieve, generate" pattern. Today there are several RAG architectures, each tuned for a different problem: document Q&A, multi-hop reasoning (questions that need several lookups), knowledge graphs, agents, structured data, codebases, and enterprise search.

That variety creates noise. Many named types come from research papers and are rarely built as described. The next section sorts the common from the rare.

4. Basic RAG

Adoption: very high. Used in production everywhere. Basic RAG is the original pattern and the base of every other type. Most internal chatbots start here, and many never need more.

4.1 How It Works

The question is turned into a vector. The vector store returns the K chunks whose vectors are closest. Those chunks and the question go to the LLM, which writes the answer.

"Closest" means closest in meaning. A question about "guarantee period" finds a chunk about "warranty" even though the words differ. This is called semantic search.

Typical uses:

  • Internal document search
  • FAQ bots
  • Knowledge base chatbots

Three things to notice:

  • LocalEmbeddings is a small adapter. LangChain expects an embedding model with two methods, embed_documents and embed_query. FastEmbed does the real work.
  • open_store returns the vector store. The vector is given the name "dense" now, because section 5 adds a second vector next to it.
  • format_chunks wraps each chunk in a tag that carries its source file. That lets the LLM say where an answer came from.

Now the indexing script.

The first run downloads the embedding model, so it takes longer. After that, the seven files have become twelve chunks, each saved with a vector of 384 numbers.

Best practice

Choose the chunk size on purpose. A chunk should hold one complete idea. Too large, and each chunk mixes several topics, so its vector matches nothing well. Too small, and a chunk loses the sentence that gives it meaning. The chunk_overlap repeats a little text between neighbours so a sentence cut at a boundary still appears whole in one of them. A few hundred characters suits short support pages like these. Long reports usually want 800 to 1,500.

Warning

The query must use the same embedding model as the index. Vectors from two different models are not comparable, and searching one with the other returns nonsense without any error. If you change EMBED_MODEL, run ingest.py again.

4.4 Retrieve and Answer

The answer should say 10 years or 6,000 charge cycles, whichever comes first, and name warranty.md as its source.

The whole of Basic RAG is the last three lines: open the store, similarity_search for the four closest chunks, and generate. Everything else in this lesson changes what happens in the retrieve step.

Best practice

Tell the model how to treat retrieved text. The system prompt above does three jobs: answer only from the chunks, say "I do not know" when they lack the answer, and treat chunk text as data. The last one matters for safety. A document can contain a sentence like "ignore your instructions". Wrapping chunks in tags and telling the model they are data makes it much harder for such text to take control. This is not a complete defence: see the warning in 9.6.

Note

The examples pass no temperature setting. Claude Opus 5.5 rejects non-default sampling settings, so older tutorials that set temperature=0 fail on it. To use a cheaper or different model, change CHAT_MODEL in common.py, for example to "anthropic:claude-sonnet-5-5".

4.5 Where It Falls Short

Try a question about one exact fault code:

The documents list four codes: F-2137, F-2173, F-2713, and F-2731. To an embedding model these strings look almost identical. They are short, and they carry no meaning it can use. So vector search ranks the chunk for F-2731 first and puts the right chunk third.

With four chunks retrieved, the right one still arrives and the LLM may answer correctly. With thousands of codes it would not arrive at all. Section 5 measures this and fixes it.

Basic RAG has three more limits, each handled by a later section:

  • It cannot tell the 2026 EU install guide from the 2025 one or the US one. Their text is nearly the same (section 6).
  • It searches once, with the user's exact words, even when a question has two parts (section 7).
  • It sees only text. A wiring diagram is invisible to it (section 8).

5. Hybrid RAG

Adoption: very high. Used in production everywhere. Hybrid RAG runs a keyword search next to the vector search and merges the results. It is the first upgrade most teams make. Some lists call it "Advanced RAG".

5.1 Why Vectors Alone Miss Exact Words

Semantic search is good at meaning and bad at exact strings. Product codes, part numbers, error codes, people's names, and rare technical terms are where it fails.

Keyword search is the opposite. It finds "F-2173" every time, but it does not know that "guarantee" and "warranty" mean the same thing.

Hybrid search runs both and combines them.

The benefits:

  • Better accuracy overall
  • Handles exact keywords
  • Handles semantic meaning

Back to top

5.2 Dense, Sparse, and Fusion

Three terms explain how hybrid search works.

A dense vector is the embedding you already have: a few hundred numbers, all filled in, that capture meaning.

A sparse vector has one slot for every possible word and is almost all zeros. Only the words that appear in the text have a value. Comparing two sparse vectors is the same as asking "which words do these texts share?"

BM25 is the standard way to score a keyword match. It gives more weight to rare words. "F-2173" appears in one chunk, so matching it counts for a lot. "the" appears everywhere, so matching it counts for nothing.

The two searches produce two ranked lists with scores on different scales, so the scores cannot simply be added. Reciprocal Rank Fusion (RRF) avoids the problem by ignoring the scores and using only the positions. A chunk near the top of either list does well. A chunk near the top of both does best.

5.5 Search and Rerank

Switching to hybrid search is one argument: mode=RetrievalMode.HYBRID. Qdrant runs both searches and applies RRF.

The example adds one more step, a reranker. Embedding models read the question and the chunk separately. A reranker, also called a cross-encoder, reads them together and scores how well the chunk answers the question. That is more accurate but too slow to run on a whole collection. So the standard pattern is: retrieve widely (here 10 chunks), rerank, keep the best few (here 3).

To see the difference without spending any LLM calls, this script prints the first line of the top three chunks in each mode.

Best practice

Fetch more candidates than you plan to use. Fusion needs material to work with. During testing for this lesson, asking hybrid search for only one result (k=1) returned the wrong chunk: each search contributed a single candidate, the two tied, and the tie broke the wrong way. With k=3 or more it was right every time. Retrieve 10 to 50, then cut down with the reranker.

Help

The second result in every row is the chunk that starts with the page title. It also contains the F-2137 section, because the chunker glued the short title onto the first section. This is chunking leaking into search quality. When results look odd, print the chunks themselves before you blame the search.

6. Metadata-Aware RAG

Adoption: very high. Used in production everywhere. Metadata-aware RAG narrows the search with exact filters before ranking by meaning. Almost every real system needs it, because almost every real collection contains text that is similar but applies to different people, places, or times.

6.1 What Metadata Is and Why It Matters

Metadata is information about a chunk that is stored next to it: which product it covers, which country, which year, what kind of document, who may read it.

The sample documents show the problem. There are three install guides for the Wall 10. They differ only in region and year, and each gives a different clearance. Ask "How much free space does the Wall 10 need around it?" and hybrid search returns all three, close together:

The LLM now holds three conflicting answers. Better search cannot fix this, because the three chunks really are the most similar text. Only a filter can: "region is EU and year is 2026".

A filter is exact. A chunk either matches or it is not considered at all. Search then ranks whatever passed the filter.

6.3 Attach Metadata at Ingest

Metadata has to be attached when the chunks are stored. Here it comes from a small table in the script. In a real system it comes from where the document lives: its folder, its fields in a content system, its access list.

The splitter copies a document's metadata onto every chunk cut from it, so all twelve chunks now carry these fields.

Best practice

Take metadata from a trusted source, not from the text. It is tempting to have a model read each document and guess its region or year. Guesses are sometimes wrong, and a wrong value hides the document from every filtered search without any error. Use the fields your content system already has, and mark documents that apply everywhere with a value such as "all".

Back to top

6.4 Filter at Query Time

Look at to_qdrant first. It builds a list of conditions and puts them in must, which means every condition has to hold. Two details:

  • The key is metadata.region, not region. LangChain stores a chunk's metadata under a metadata field in the Qdrant payload.
  • The region condition uses MatchAny with the region and "all". Otherwise a filter for the EU would hide the warranty policy, which applies everywhere.

With region set to eu and year set to 2026, the same search that returned three install guides now returns one:

The other three results are documents marked "all". They pass the filter and fill the remaining places.

Note

On a Qdrant server, create a payload index for each field you filter on, so filtering stays fast on large collections: client.create_payload_index(COLLECTION, "metadata.region", models.PayloadSchemaType.KEYWORD). Local mode accepts the call but does not need it.

Back to top

6.5 Let the LLM Build the Filter

Users do not fill in filter forms. They type "the 2026 Wall 10 in the EU". Something has to turn those words into filter values. Asking the LLM to do it is called self-query.

That is what extract_filter does. SearchFilter describes the allowed fields and values. with_structured_output makes the model reply with an object of exactly that shape instead of free text. A field the question does not mention stays empty, and an empty field adds no condition.

The script prints the filter it extracted, then the answer. For the default question the filter should contain region eu and year 2026, and the answer should be 30 cm at the sides and 50 cm above.

Note

The call uses method="json_schema". The default method in langchain-anthropic 1.7.5 forces the model to call a tool, and the newest Claude models reject forced tool calls. json_schema uses Claude's structured output feature instead.

Warning

Never let the model choose a filter that controls access. Self-query is fine for convenience filters like year or document type. A wrong guess there gives a worse answer, nothing more. A filter that decides what a person is allowed to see (their tenant, their department, their clearance) must be set by your code from the logged-in user. Otherwise a user can type "I am in the US team" and read US-only documents. lock_region in the file above shows the pattern: whatever the model extracted, your code overwrites it.

7. Agentic RAG

Adoption: high and growing. Common in production. In the first three types, your code decides what to retrieve. In Agentic RAG, the LLM decides. This is where most new RAG work is happening.

7.1 From a Fixed Pipeline to a Loop

The pipeline so far always does the same thing: search once with the user's words, then answer. An agent is an LLM running in a loop with tools. A tool is a function the model may ask your program to run. After each result the model decides what to do next.

In Agentic RAG the LLM decides:

  • what to search for
  • where to search
  • how many times to search
  • whether more retrieval is needed

Take this question about the sample documents: "Which model suits a home with a heat pump, and is it covered if I install it outdoors?"

One search with those words returns a blend of chunks that answers neither half well. An agent can work through it:

  1. Search the product guide for heat pumps. Result: the Stack 15 is recommended.
  2. Now it knows which model to ask about. Search the outdoor rules for the Stack 15. Result: indoor use only, and outdoor installation voids the warranty.
  3. Combine both: the right model for the heat pump cannot go outdoors.

The second search depends on the first answer. No fixed pipeline could have written it in advance. This is the "multi-hop" idea from section 2, and an agent gives it to you without special machinery.

7.3 Retrieval as a Tool

The shortest route to Agentic RAG: turn your retriever into a tool and give it to a prebuilt agent.

The script prints each search the agent chose to make, then the answer. Expect at least two searches, and an answer that recommends the Stack 15 for the heat pump and warns that installing it outdoors voids the warranty.

How the parts fit:

  • @tool turns the function into a tool. The model never sees the code. It sees the name, the parameters, and the docstring.
  • create_agent builds the loop: call the model, run any tool it asks for, send back the result, repeat until the model answers in plain text.
  • The tool reuses to_qdrant from section 6, so the agent can narrow a search by document type when it wants to.

Best practice

Write the tool's docstring for the model. It is the only guidance the model has about when and how to search. Say what the tool searches, what a good query looks like, and when to call it again. The docstring above tells the model to use short, specific queries and to search more than once for questions with several parts. Vague docstrings are the most common cause of an agent that searches badly.

7.4 A Grade-and-Rewrite Loop in LangGraph

A prebuilt agent trusts whatever the search returns. Sometimes you want a fixed quality check: look at the retrieved passages, and if they do not answer the question, search again with different words. This is the useful core of CRAG.

LangGraph lets you draw that as a graph. A node is a step, a plain function. An edge says which step comes next. A conditional edge picks the next step from the current state.

The path through the graph:

  1. decide: the model calls the search tool, or answers directly if no search is needed (for "hello", say).
  2. retrieve: LangGraph's ToolNode runs the search.
  3. grade: a second model call judges whether the passages contain the answer. It is a conditional edge, so its return value names the next node.
  4. rewrite adds a hint and returns to step 1. Or answer writes the final reply.

The state carries the original question and a rewrites counter. The counter is what makes the loop safe: after two rewrites, grade goes to answer whatever the passages look like.

Help

Start with create_agent. Move to an explicit graph only when you need a step the prebuilt loop does not have, such as this grading check, a human approval, or a different model for one step. The graph gives you control, and you pay for it in code you have to maintain.

Back to top

7.5 Cost, Latency, and a Step Limit

Agentic RAG costs more than a pipeline. Basic RAG makes one LLM call per question. The heat pump question typically takes three: two that choose a search and one that answers. The graph version adds a grading call after every search. Each call adds waiting time and money.

So agentic is not automatically better. If most questions are simple lookups, a hybrid pipeline with filters is faster, cheaper, and easier to debug. Many systems use a pipeline for the common case and an agent only where questions really are multi-part.

Best practice

Always cap the loop. An agent that keeps getting poor results can keep searching without end. Both examples have a cap. Set one from the start, then tune the number by watching real questions.

8. Multimodal RAG

Adoption: medium-high and increasing. Multimodal RAG retrieves and reasons over more than plain text. It is growing fast because vision-capable LLMs have become good and cheap, and because so much business knowledge sits in PDFs full of tables, charts, and diagrams.

8.1 What Changes When Content Is Not Text

"Multimodal" means more than one kind of content:

  • Text
  • Images (photos, diagrams, charts, screenshots)
  • PDFs, which mix text, tables, and pictures on a page
  • Audio
  • Video

The difficulty is that a text embedding model cannot read a picture. If the answer exists only in a diagram, no text chunk contains it, so text search can never find it.

There are two ways round this, described in 8.3 and 8.4. The code in this lesson covers PDFs and images. Audio and video are usually handled by converting them first: a speech-to-text model produces a transcript, and video is sampled into frames plus a transcript. After that they are text and images, and the same methods apply.

8.3 Approach A: Describe the Picture, Then Index the Text

The common production approach is simple. At indexing time, show each picture to a vision model and ask it to write a description. Store the description as a normal text chunk, with a pointer to the picture file in its metadata.

Search does not change at all. The description is text, so dense, sparse, and hybrid search all work on it.

First, a PDF to work with. This script makes a one-page manual whose wiring diagram is a real picture, so its labels cannot be read as text.

The page text says only "Connect each cable to its terminal as shown in Figure 1". Which cable goes to which terminal is in the picture alone: three boxes labelled X1, X2, and X3, with "GRID cable" under X1.

Now index it.

For each page the script stores the page text as one chunk. For each picture on the page it saves the picture to extracted_images/, asks Claude to describe it, and stores the description as a second chunk with kind set to "image" and image_path pointing at the file.

The picture goes to the model as a content block: a message whose content is a list of parts, here one image and one piece of text. The image travels as base64, a way of writing binary data as plain characters.

Best practice

Ask for a description written for search, not a caption. "A wiring diagram" is a caption, and it matches almost no question. The prompt above asks for every label and what connects to what, because those are the words a user will type. The description is the only thing search can see, so anything it leaves out cannot be found.

Warning

multimodal_ingest.py adds chunks to the existing collection, and ingest.py wipes the collection and rebuilds it from the Markdown files. If you run ingest.py again, run multimodal_ingest.py after it. Running multimodal_ingest.py twice in a row stores the manual twice.

8.4 Approach B: Embed the Pictures Directly

The second approach skips the description. A multimodal embedding model turns text and images into vectors in the same space, so the vector for the question "grid cable terminal" lands near the vector for the diagram itself.

Two families are in use:

  • One vector per image or page. A hosted model such as Voyage voyage-multimodal-3.5 takes images and text and returns one vector for each. That fits any vector store.
  • Many vectors per page. ColPali and ColQwen embed a screenshot of the whole page as hundreds of small patch vectors and compare them with the question word by word. This is called late interaction. It is the most accurate option for pages dense with charts and tables, and it needs no PDF parsing at all. It also needs far more storage and a store that supports multi-vector search.

Finding the right chunk is half the job. A description is a summary, and summaries lose detail. So when a retrieved chunk came from a picture, attach the original picture to the prompt and let the LLM look at it.

9. How an LLM Uses RAG and MCP Together

This is one of the biggest points of confusion in modern AI architecture. RAG and MCP often appear on the same diagram, so people assume one feeds the other. They do not.

MCP is the Model Context Protocol, a standard way for an LLM application to connect to outside tools and data. An MCP server offers tools. An MCP client, inside the LLM application, calls them. The companion lesson covers it in depth.

9.1 The Short Answer

  • RAG does not talk to MCP.
  • MCP does not talk to RAG.
  • The LLM orchestrates both.
  • RAG and MCP solve different problems.

Think of it like this:

ComponentPurpose
LLMBrain
RAGMemory / search
MCPTool access
External systemsDatabases, APIs, services

RAG is a technique: look things up, then answer. MCP is a protocol: a standard plug for connecting tools. Comparing them is like comparing "reading the manual" with "a USB port". One is something you do. The other is how things get connected.

Back to top

9.2 Where RAG Sits

In a modern system, RAG is usually implemented as a tool. You saw this in section 7: search_support_docs is a tool, and the model calls it.

The LLM does not query the vector database directly. It cannot. An LLM only produces text. What it produces is a request: "call search_support_docs with this query". Your code, the retrieval service, runs the search and returns the chunks.

That retrieval service may be exposed through MCP. This is the only place the two meet. MCP is one way to deliver the tool to the model. A plain Python function, as in section 7, is another. The retrieval code inside is the same either way.

Back to top

9.3 Flow 1: RAG Only

The user asks: "How long is the battery warranty?" The answer is in a document. Nothing else is needed.

  1. The user asks the question.
  2. The retriever searches the embeddings.
  3. The relevant chunks are returned.
  4. The chunks are injected into the prompt.
  5. The LLM generates the answer.

This is basic_rag.py exactly. There is no MCP anywhere in it. In the agentic version the LLM triggers step 2 itself by calling the search tool, but the data still comes from documents.

Back to top

9.4 Flow 2: MCP Only

The user asks: "When was unit EMB-W10-004512 installed?" No document contains this. It is a fact about one customer, held in a live system that changes every day.

  1. The user asks the question.
  2. The LLM sees a tool named get_purchase_record and asks to call it with the serial number.
  3. The MCP client sends the call to the MCP server.
  4. The server reads the order system and returns the record.
  5. The LLM generates the answer from the record.

There is no RAG here: no chunks, no embeddings, no similarity search. The lookup is exact, by serial number.

A rule of thumb for which one a piece of knowledge needs:

The knowledge isReach it withExample
Written text that changes slowly, found by meaningRAGPolicies, manuals, product guides
A live fact, found by an exact keyA tool (often through MCP)An order, an account balance, today's stock level
An action that changes somethingA tool (often through MCP)Open a ticket, send an email, book a visit

9.5 Flow 3: Both in One Answer

The user asks: "My unit is EMB-W10-004512. Is the battery still under warranty?"

Neither source can answer alone. The warranty rule (10 years from the installation date) is in a document. The installation date of this unit is in the order system.

  1. The user asks the question.
  2. The LLM calls search_support_docs for the warranty rule. This is RAG. It returns the chunk from warranty.md.
  3. The LLM calls get_purchase_record with the serial number. This is a live lookup. It returns the install date, 14 March 2019.
  4. The LLM combines them: 10 years from March 2019 runs to March 2029, so the battery is still covered.

The two tools never contact each other. The search tool does not know the order system exists, and the order tool knows nothing about documents. The LLM reads both results and joins them. That is what "the LLM orchestrates both" means.

9.6 Build It: Server and Agent

This MCP server offers both tools. The search tool is the hybrid retriever from section 5 behind an MCP decorator. The purchase tool stands in for a real order system.

Compare search_support_docs here with the one in agent_rag.py. The body is the same retrieval call. Only the decorator changed, from LangChain's @tool to FastMCP's @mcp.tool. That is the whole meaning of "RAG exposed through MCP".

The gain from MCP is reuse. Any MCP client can now use this retriever without importing your Python code: Claude Code, Claude Desktop, an IDE assistant, or an agent written in another language.

Next, an agent that connects to the server and uses both tools.

The script prints each tool call, then the answer. Expect one call to search_support_docs and one to get_purchase_record. The answer should say the battery modules are covered until March 2029 and the inverter's five-year cover ended in March 2024.

How it works:

  • Client(Path("support_mcp_server.py")) starts the server as a child process and talks to it over stdio (standard input and output).
  • client.list_tools() asks the server what it offers. The agent learns the tool names, descriptions, and parameters at run time. Nothing about the tools is written into the agent.
  • as_langchain_tool wraps each MCP tool so the LangChain agent can call it. A call goes: model, then wrapper, then MCP client, then MCP server, then your function.

Note

The wrapper is written by hand for a reason. The usual bridge, langchain-mcp-adapters 0.3.2, requires the mcp package below version 2. FastMCP 4 requires version 2 or above. The two cannot be installed together today. The twelve-line wrapper avoids the conflict.

Help

To try the server from Claude Code instead, register it with claude mcp add emberline -- python support_mcp_server.py, run from the project folder with the virtual environment active. Section 7 of the MCP lesson explains the options. Qdrant local mode lets only one process open the data folder at a time, so do not run the other scripts while Claude Code has the server running.

Warning

Retrieved text is untrusted input, and an agent with tools can act on it. In a pure RAG chatbot, a poisoned document can at worst produce a wrong answer. Once the same model also holds tools that read customer records or change things, a document containing hidden instructions can try to make the model misuse those tools. This is called retrieval poisoning. Keep the "treat passages as data" instruction, give the agent only the tools it needs, and require approval for actions that change anything. The MCP lesson covers the attack and its defences in section 10.3.

Summary

  • RAG means looking up relevant text and putting it in the prompt, so the model answers from your documents instead of from memory.
  • Every RAG system has an indexing phase (load, chunk, embed, store) and a query phase (retrieve, augment, generate).
  • Of more than a dozen named RAG types, a few carry most production systems. Many of the others are research ideas, or are absorbed into Agentic RAG.
  • The five common types stack: Basic searches by meaning, Hybrid adds exact words and a reranker, Metadata-Aware adds filters, Agentic lets the model drive the search, and Multimodal adds pictures.
  • RAG and MCP do different jobs. RAG is how the model looks things up in documents. MCP is a standard way to connect tools. The LLM calls both, and they never call each other.
  • RAG is usually delivered to the model as a tool. Whether that tool is a local function or an MCP tool does not change the retrieval code.

Which type do you need?

If your users askYou need at least
General questions answered by one passageBasic
Questions containing codes, IDs, names, or exact termsHybrid
Questions where the right answer depends on region, date, product, or who is askingMetadata-Aware
Questions with several parts, or follow-ups that depend on the first answerAgentic
Questions answered by a chart, table, diagram, or scanMultimodal
Questions that also need live data or an actionAny of the above, plus tools (often through MCP)

Where to go next: learn RAG evaluation, which is how you measure whether a change to chunking, search, or prompts helped (Ragas is the usual starting point). Then look at SQL RAG for questions over database tables, the one widely used type this lesson left out.
